Two things worth knowing

The diagram above is drawn as the everything-succeeds path.

Fixed this session

The DMS connection no longer needs its own secret

Before: KaroDmsConnectionResolver looked up a flat Karo:DbCredentials:ConnDMSDB{practiceSuffix} secret that was never configured in this environment — every document write failed with "connection target is not configured." Confirmed from the real legacy Web.config that the DMS connection shares its server and credentials with the primary practice connection, only Initial Catalog differs (DMS_PMS vs the practice DB). Now it resolves through the same TenantRegistryService route as KaroPracticeConnectionResolver and just swaps the database name.

Real bug, not fixed here

uspDocumentSave itself has a transaction bug

With the connection now resolving correctly, the real stored procedure throws "The ROLLBACK TRANSACTION request has no corresponding BEGIN TRANSACTION" from inside its own TRY/CATCH — a genuine bug in the deployed SQL, unrelated to this project's code. Confirmed live this session; needs a SQL-side fix, out of reach from the API layer.
