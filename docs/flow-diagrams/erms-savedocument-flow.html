Three things worth knowing

The diagram above is drawn as the everything-succeeds path.

Bug found + fixed this session

Wrong XML tag names silently nulled the request

ReferralDocument's real [XmlElement] names are ReferralDocument_Encounter_ID, ReferralDocument_Patient_PMS_ID, etc — not the plain <EncounterID> the dashboard client used to send. XmlSerializer doesn't error on an unmatched element, it just leaves the property null — so patientId/encounterId/routing all silently fell through to empty/unscoped before this was traced and fixed.

Fixed this session

DMS connection, same fix as KARO's

ErmsDmsConnectionResolver now resolves through the same TenantRegistryService route as the primary connection and swaps the database name to DMS_PMS, instead of needing its own separate, never-configured secret.

Real bug, not fixed here

uspDocumentSave's transaction bug, confirmed shared

With routing and XML tags both fixed, this call reaches the exact same "ROLLBACK TRANSACTION ... no corresponding BEGIN TRANSACTION" failure as KARO's document write — confirming it's the one shared dbo.uspDocumentSave procedure on DMS_PMS, not a per-system bug.
