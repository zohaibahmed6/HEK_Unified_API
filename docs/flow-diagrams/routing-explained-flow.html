How routing actually works: HISO vs KARO/ERMS/COL

Two genuinely different mechanisms decide "which real SQL Server, which real database" for a request — HISO uses one central table keyed by its own session GUID; KARO, ERMS, and COL share a second table keyed by a composite practice identity parsed out of the encounter ID. Traced from the real, verified source in this repo, including the exact matching rule and a real routing bug found and fixed this session.

Two separate registry tables, one database

Both live in the same HekTenantRegistry SQL Server database, but they're queried completely differently and never share a row.

TableUsed byLooked up byReal columns
Practices KARO, ERMS, COL (COL reuses ERMS's own resolver) A 4-part composite key: PracticeId + PracticeCode + Environment + SourceSystem PracticeId, PracticeCode, Environment, SourceSystem, DbServerHost, DbName, RowLevelSecurityEnabled, IsActive
HisoSessions HISO only The session's own SessionGuid (or, in a few call sites, PracticeId alone) SessionGuid, PracticeId, PracticeCode, Environment, PracticeName, SourceSystem (always "Hiso"), DbServerHost, DbName, RowLevelSecurityEnabled, IsActive

Confirmed in code: HisoSessionRegistryEntry.cs is deliberately shaped to mirror Practices field-for-field, plus SessionGuid — but it is a genuinely separate table. A HISO row is self-sufficient: it already carries its own DbServerHost/DbName, so resolving a HISO session never has to go back and query Practices.

The exact matching rule

Confirmed from TenantRegistryService.ResolveRouteAsync — the SourceSystem filter is conditional, not always applied.

Two lookup modes, one method

Flat PracticeId vs full composite

The 29 "generic" legacy repositories that never learned their own origin call ResolveRouteAsync(string practiceId), which quietly becomes RoutingContext.FromPracticeId(practiceId, Unscoped) — PracticeCode/Environment both default to "-", and the SourceSystem filter is skipped entirely. KARO/ERMS's own resolvers always call the full RoutingContext overload instead.

Real, confirmed live

Same PracticeId can be two different rows

Practice 901 has two real rows in Practices — one with SourceSystem="Karo", one with SourceSystem="Erms", both currently pointing at dbserver-local/PMS_NZ_V2 in this environment, but architecturally free to diverge (e.g. the same practice on Karo vs Erms in different real environments).

The DMS twist: same route, different database name

Fixed this session — the DMS (document storage) connection is not a separate registry entry.

Confirmed from the real legacy Web.config

DMS shares the server and credential, only the catalog differs

KaroDmsConnectionResolver/ErmsDmsConnectionResolver now call the exact same ResolveRouteAsync(routingContext) as the primary connection resolvers, reuse the same DbServerHost and the same credential secret, and only swap Database to DMS_PMS (default, configurable via Erms:DmsDatabaseName/Karo:DmsDatabaseName). Before this fix, each DMS resolver looked up its own flat {System}:DbCredentials:ConnDMSDB{practiceSuffix} secret that was never configured — every document write failed with "connection target is not configured," independent of whether the primary connection worked.
