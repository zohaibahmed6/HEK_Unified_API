## 2. Confirmed Facts (don't re-derive these)

### System overview
- Three legacy systems: **HISO** (WCF SOAP, ACC45 accident-claim forms, NZ HISO 10014.2 standard), **KARO/HSSWebAPI** (bridges Indici PMS to HSS portal), **ERMS/ERMSWebAPI** (eReferrals XML + undocumented COL/Pegasus JSON claiming integration).
- All three share a `DAL` codebase (identical subfolder/class names, identical hardcoded secrets, identical SQL-injection code smells in dormant modules).

### Production topology (⚠️ corrected 2026-07-19 — supersedes the SRS's stated assumption)
- The SRS assumed "one shared Indici PMS database" (§4.4). **This does not match real production**, per direct stakeholder confirmation: ERMS and KARO/HSS run from one app server that already routes to **different physical database servers depending on the calling practice**; HISO runs on **multiple IIS servers, each bound to its own specific database server**. Some database servers already host more than one practice's data together.
- The earlier finding that KARO and ERMS share identical code/stored-procedure names (`[HSS]` schema, `uspGetDemographics` etc.) is still accurate — that's a code-duplication fact, separate from physical topology, which is sharded.
- **Architecture decision (ADR-001):** No consolidation into one physical database. Instead: one small tenant/practice registry database (replacing `Web.config` connection-string lists) that the API looks up per request to route to the correct physical server; row-level security (RLS) applied on any server hosting more than one practice.

### Enterprise Architecture decisions (ADR log, approved 2026-07-19)
| ADR | Decision (one line) |
|---|---|
| ADR-001 | Tenant registry DB routes to existing sharded physical DB servers; RLS on shared servers. No data migration. |
| ADR-002 | Real auth via a managed identity platform (Entra ID/Okta/Auth0 — vendor TBD), fronted by a compatibility adapter so HSS Portal and ERMS keep their exact current request shape. |
| ADR-003 | Tokens scoped to one patient+encounter+practice; origin scope (KARO/HISO/ERMS) determined structurally by which credential/entry-point authenticated the request — never by a self-reported field. |
| ADR-004 | HISO keeps its existing session-GUID mechanism as-is; adds a 12-hour expiry and logs failed lookups as security events (currently silently swallowed). |
| ADR-005 | Docker containers, load-balanced across identical instances; cloud/host TBD. |
| ADR-006 | Balanced HA/DR: multi-region active-passive, pilot-light DR. Explicitly provisional — no real RTO/RPO figures exist yet. |
| ADR-008* | Every new capability, including auth/security itself, ships behind a config toggle (off by default) — flagged by the Review Board as the one item needing an owner and enable-by date before production. |

*ADR numbering in the source document runs to ADR-011 (routing, HTTPS-everywhere, no schema changes, ERMS/HSS failover pair) — full detail is in the ADR document once it's copied into this folder (see Action Item above).

### Security findings (hard blockers — from Phase 1-3 analysis, unchanged)
- Identical hardcoded SQL symmetric-key password (`tcpepms*1`) shared across HISO/KARO/(likely)ERMS.
- KARO and ERMS ship byte-identical DAL code including a live SQL injection in `DMSDA.cs` (confirmed via direct inspection).
- No real authentication in any of the three systems today — addressed by ADR-002/003/004.
- Thread-unsafe static shared DB connection in HISO (`DbAccess.cs`).
- ERMS has the most exposed credential footprint: 15 connection strings in `Web.config`, several pointing at a public IP.
- All three: no automated tests, no rate limiting, no security-event/audit logging, PHI/secrets logged in plaintext.

### API Contract Design decisions (Phase 7, approved 2026-07-19)
| Decision | Resolution |
|---|---|
| Response format (SRS §13.3, previously deferred) | One canonical JSON/REST contract internally; every existing consumer (HSS Portal, ERMS eReferrals, COL/Pegasus, HealthLink engines) keeps its exact current wire shape via edge compatibility adapters — resolved by inference from ADR-002/004/007's established "zero consumer-side change" pattern, not asked as a fresh question. |
| Versioning | **Stakeholder decision:** no version identifier in URL/header/media-type; version tracked in documentation only (OpenAPI `info.version` + changelog). No request/response change may ship without a coordinated migration. |
| Error format | **Stakeholder decision:** errors must not display any data. RFC 7807-inspired shape, but `detail`/`errors[].message` are always generic/static — never PHI, never exception text. Full detail goes to server-side structured logs only, correlated via `traceId`. |
| Pagination | **Stakeholder decision:** none in v1 — third-party consumers have no pagination handling on their end. List endpoints return the full filtered set inside `{"items": [...]}`, left pagination-ready for a future non-breaking addition. Accepted as a scalability risk, not an oversight (see Contract Design doc §19). |
| Idempotency mechanism | Optional `Idempotency-Key` header + natural-key fallback (for legacy edge adapters that won't send the header); duplicate write returns `200` with the existing resource, replacing KARO's `-5`/`-3` and ERMS COL's `-3` magic codes. |
| Document classification (FR-DOC-03) | Both `direction` (in/out) and `contentType` (MIME) kept as independent first-class fields on the canonical `Document` schema — shape resolved, but the combined filing/mapping *logic* is left open for Implementation Planning (no source document specifies it). |

### Demographics (and other union-shaped) response reconciliation — deferred, not merged (2026-07-19)
- **Zohaib decided: keep HISO's, KARO's, and ERMS's response shapes separate for now** rather than have the contract force them into one merged/canonical field set, because he doesn't currently have sample live responses or the time to do the field-by-field comparison. To be revisited later.
- **This is a real change to the API Contract Design document**, not just a closed checklist item. The document as currently written (Section 6.2, `GET /patients/{patientId}/demographics`) assumes one canonical merged shape produced by edge adapters translating *into* it. "Keep separate" instead implies either: (a) the canonical endpoint returns whichever legacy system's shape matches the caller's origin scope, unmerged, or (b) three distinct endpoints/response variants exist side by side until reconciliation happens. **Resolved 2026-07-19: Option B — "as previously implemented."** Each legacy system keeps its own separate endpoint/shape (HISO's `getData`-based demographics, KARO's `GetDemographics`, ERMS's `GetPatientData`) rather than one shared canonical path that switches shape by caller origin. No single merged `/patients/{patientId}/demographics` endpoint — this needs to be undone in the contract document, which currently only has the one merged version. Joins the still-pending contract-document revision action item (alongside the earlier KARO/HISO dead-code un-exclusions).
