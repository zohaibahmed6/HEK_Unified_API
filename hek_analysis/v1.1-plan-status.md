**KARO/ERMS/COL auth mystery SOLVED (2026-07-24, with Zohaib live)**: root cause was a real, genuine bug, not a business rule - `int.TryParse` (32-bit) on real Indici appointmentIds, which are `long` (confirmed by Zohaib). A real appointmentId (`2147488418`) exceeds `Int32.MaxValue` (`2147483647`), so the overflow check silently misfired and routed the value through `Decrypt()` instead of passing it straight through - `Decrypt()` then threw internally on non-ciphertext input and its catch block returned an **empty string**, so the API was silently sending `@pAppointmentID=''` instead of the real value. Confirmed by comparing our C# code's actual behavior against a direct `sqlcmd` `EXEC` of the same real stored procedure with the same real parameters - the manual call succeeded (real token returned), proving the DB/SP/credentials were never the problem. Fixed in all 4 real occurrences (`KaroRequestParser.cs`, `ErmsRequestParser.cs` ×2, `ColRequestParser.cs`) - `int.TryParse` → `long.TryParse`. **Verified live**: KARO `/karo/authenticate` with `hsslive`/practice 901/appointmentId `2147488418` now returns a real success token (`a895dc03-f4ef-485f-ad34-7874ebc76c10`), matching Zohaib's manual `EXEC` result exactly. **ERMS and COL also confirmed fixed and verified live** (2026-07-24): ERMS returned a real token (`a73cc723-...`, practice `maraenui`) - also caught a second, unrelated bug in my own test payload along the way (wrong XML root element `<ErmsCredential>` instead of the real `<Credential>` per `[XmlRoot("Credential")]` - not a code bug, my test was wrong). COL returned a real token (`98576584-...`, same practice `maraenui`). All three systems (KARO/ERMS/COL) now genuinely authenticate successfully against real local practice 901 data.
