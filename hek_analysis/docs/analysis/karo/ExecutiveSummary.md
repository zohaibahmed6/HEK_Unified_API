# KARO (HSSWebAPI) — Executive Summary

## System Overview

KARO (repository/namespace `HSSWebAPI`) is a legacy ASP.NET Web API 2 application that exposes a single, large, monolithic controller (`APIController.cs`, 2,047 lines) implementing a bespoke integration contract between the **Indici Practice Management System (PMS)** and the **Health Systems Solutions (HSS) portal**. It is a clinical-data bridge API: given an encrypted `patientId`/`encounterId` and a bearer token, it lets the HSS portal read and write patient demographics, clinical notes, conditions, medications, lab results, observations, recalls, documents/attachments, invoices, and free-form "encounter summary" clinical templates (diabetes review, foot exam, retinopathy, etc.) against a SQL Server–backed PMS database (`PMS_NZ*` / Indici schema `[HSS]`).

The solution consists of three projects sharing one repository root (`E:\NZTFS\hsswebapi\DevLocal`):
- **HSSWebAPI** — the ASP.NET Web API 2 (OWIN-hosted, but OWIN `Startup.Configuration` is empty) presentation layer. One controller (`APIController`), no service layer, no repository abstraction.
- **DAL** — a shared, multi-tenant ADO.NET data-access library with 12 subject-area folders (BPAC, BPI, DMS, GP2GP, MHNAppointment, MHNHL7, Pegasus, Procare, Procon, Screening, South, UI, HelperClasses). Evidence shows **only the `South\HSSDA.cs` class is actually called by APIController.cs** — the other 11 modules are compiled into the same DAL.dll but appear to be dead code from KARO's perspective, most likely shared with sibling systems referenced by the `.csproj` hint path `..\..\MHNPHMP-Integration\Logger\bin\Debug\Logger.dll` (i.e., this repo is a subset of a larger multi-app solution).
- **Logger** — a simple flat-file logger (`Logging.cs`) with no correlation IDs, no log rotation limits, and no redaction — it logs full request payloads including plaintext usernames/passwords.

## Technology Stack Summary
.NET Framework 4.8 (project target; some references at 4.5.2/4.6.1), ASP.NET Web API 2.2 (System.Web.Http 5.2.x) hosted via OWIN/`Microsoft.Owin.Host.SystemWeb`, ADO.NET (`System.Data.SqlClient`) against SQL Server via stored procedures, Newtonsoft.Json 13.0.1, Entity Framework 6.1.3 referenced but not used in the traced code path, `Microsoft.AspNet.Identity.*` and full OWIN OAuth/Cookie/Google/Facebook/Twitter/MicrosoftAccount packages referenced but **never wired up** (empty `Startup.cs`). See `TechnologyStack.md`.

## Architecture Style
Two-tier, non-layered **"Fat Controller + Static DAL"** monolith. No dependency injection, no interfaces/abstractions, no unit tests found, no service layer — the controller calls static `HSSDA` methods directly, which call a hand-rolled ADO.NET helper (`DALHelper`/`DbAccess`). See `Architecture.md`.

## Counts (from source, KARO/HSSWebAPI project only)
- **HTTP endpoints (controller actions):** 24 (Ping, Authenticate ×2 overloads/verbs, 14 GET reads, 8 POST writes) — see `EndpointInventory.md`.
- **Business rules extracted:** 22 — see `BusinessRules.md`.
- **Distinct DB connection string targets referenced across the whole DAL:** 12 (`ConnIndiciDB[+env]`, `ConnDMSDB[+env]`, `ConnBPI`, `ConnGP2GP`, `ConnMHN`, `ConnMHNBPAC`, `ConnMHNDMS`, `ConnMHNDataMigration`, `ConnMHNHL7`, `ConnMHNPMS`, `ConnMasterDatabase`, `ConnulmDB`) — only `ConnIndiciDB*` and `ConnDMSDB*` are actually reachable from KARO's controller.
- **Stored procedures invoked by the reachable code path (`HSSDA`):** ~35, all under the `[HSS]` schema of `PMS_NZ*`, plus `[dbo].[uspDocumentSave]`/`[dbo].[uspDocumentDelete]` in the DMS database.

## Top 5 Security Issues
1. **No authentication/authorization framework is configured.** `Web.config` sets `<authentication mode="None"/>`, and `Startup.cs`'s OWIN `Configuration(IAppBuilder app)` method body is empty despite full OAuth/Identity/Cookie NuGet packages being referenced. All "auth" is a bespoke bearer-token string validated inside a stored procedure and manually read from the `Authorization` header in each action (`APIController.GetAuthorizationToken()`). (`Web.config` lines 44-45; `Startup.cs`; `Controllers\APIController.cs` line 1976-1987)
2. **Wide-open CORS.** `[EnableCors(origins: "*", headers: "*", methods: "*")]` on the entire controller. (`Controllers\APIController.cs` line 22)
3. **Confirmed SQL injection via string concatenation** in DAL classes reachable from other apps sharing this DAL.dll (`DMSDA.cs` line 27, `DBMessages.cs` lines 797/827/864) — not reachable from KARO's own controller today, but shipped in the same compiled artifact and a serious risk if any caller passes user input into `templateIDs`/`InboxFolderItemID`/`jsonString`.
4. **Hardcoded cryptographic secrets** in source: a static 256-bit Rijndael key in `Models\EncryptionManager.cs` (line 47) used to "encrypt" patient/encounter IDs, and a hardcoded SQL Server symmetric-key decryption password (`'tcpepms*1'`) in `DAL\HelperClasses\DALHelper.cs` (line 17). Database connection strings with plaintext passwords are committed directly in `Web.config`.
5. **PHI and credentials written to plaintext log files.** `Authenticate` logs the raw `username`/`password` query values; nearly every action logs full patient identifiers, clinical note text, and diagnoses to daily flat files under `Logs\` with no access control or redaction. (`Controllers\APIController.cs` line 62, 132, 876-877)

## Top 5 Risks (for migration)
1. **Undocumented, silently-mocked endpoint:** `GetEncounterSummary` (GET) returns **hardcoded sample JSON** regardless of the requested patient for `identifier=diap`/`cvra`, and `{}` otherwise — this is either dead/test code left in production or a functionally broken endpoint; either way it must be understood before being ported. (`Controllers\APIController.cs` lines 439-444)
2. **`SaveScreeningCode` is a stub** — it deserializes and logs the POST body then unconditionally returns `{"status":"success"}` without persisting anything. Any downstream consumer believes data was saved when it was not. (`Controllers\APIController.cs` lines 1924-1947)
3. **Multi-tenant routing via string concatenation of connection-string names** (`"ConnIndiciDB" + practiceid`, where `practiceid` is derived by splitting a client-supplied `encounterId`). This is a fragile, implicit multi-tenancy mechanism with no central tenant registry — a wrong/missing config entry throws unhandled `NullReferenceException`s that get swallowed into generic error strings.
4. **All HTTP responses return `200 OK`** regardless of actual outcome (`SetToJson` always sets `HttpStatusCode.OK`; errors are communicated only inside the JSON body). Any modern gateway, monitoring, or client library that relies on HTTP status codes will silently treat failures as successes.
5. **11 of 12 DAL subsystems (BPAC, BPI, DMS, GP2GP, MHNAppointment, MHNHL7, Pegasus, Procare, Procon, Screening, UI) are compiled into KARO's dependency graph but are not called by KARO's own controller.** Migrating "the whole DAL" verbatim would import large amounts of unrelated/dead code (including the SQL-injectable methods above) into the new unified platform unless scoped deliberately to the `South\HSSDA.cs` surface actually used by this API.

## Overall Recommendation
KARO should be treated as a **narrow, single-purpose clinical-data exchange adapter** (Indici PMS ↔ HSS portal), not as a general platform API. When folding it into the unified platform, port only the ~24 endpoints and the `HSSDA` stored-procedure contract that are demonstrably exercised by `APIController.cs`; do not carry forward the rest of the shared DAL, the dead `Enums.CallType` list, the empty OWIN Identity scaffolding, or the hardcoded encryption/connection-string patterns. Before any rewrite, the team must get authoritative answers on (a) what `GetEncounterSummary`'s mocked responses were supposed to do, (b) whether `SaveScreeningCode` was ever functional in another system, and (c) the real list of tenants/practices behind the `practiceid` suffix convention, since none of this is documented and all three are load-bearing for correctness.
