# ERMS Web API — Business Rules Catalog

## Summary
20 business rules were extracted from `APIController.cs`, `COLController.cs`, `HSSDA.cs`, `PHCO.cs`, and `EncryptionManager.cs`. Most cluster around three themes: (1) how a request's practice/tenant context is derived from an opaque `EncounterId`, (2) how identifiers are obfuscated/decoded, and (3) data-shaping rules applied after stored-procedure calls (ordering, date windows, RTF conversion).

## Risks
- Rules BR-01 through BR-04 (practice-id-in-EncounterId, double-encoding, Azure-forwarding) are undocumented, tightly coupled, and load-bearing for every single endpoint — any migration that changes how tenant context is passed must explicitly re-implement this logic or coordinate a breaking change with the ERMS consumer.
- BR-06/BR-07 (token re-validated per-call against DB, short expiry) mean the "auth" system is really a session-context lookup, not a bearer token in the OAuth sense — assuming JWT-like statelessness during migration would be incorrect.
- BR-09 (per-practice AWS/on-prem DMS split) is state that lives outside this codebase (in the Indici DB); it must be inventoried before any DMS-related endpoint is migrated.

## Recommendations
- Validate BR-01 through BR-04 with the client/ERMS integration owner before deciding how tenant/practice context will be carried in the unified API's request contract.
- Treat BR-06/BR-07 as the actual authentication design intent for Phase 4 comparison — not a defect, but a pattern to explicitly replace with OAuth2/OIDC + short-lived tokens or DB-backed sessions, whichever the unified platform chooses.
