# ERMS Web API — Migration Risk Assessment

## Summary
ERMS's migration risk is dominated not by its size (30 endpoints, relatively small) but by hidden/undocumented behavior — an entire second API surface, an ID-obfuscation scheme load-bearing for access control, and practice-routing logic entangled in every action — plus a legacy framework that requires a full rewrite rather than a port, and a shared DAL project whose true ownership boundary is unclear.

## Risks (things dangerous to silently drop during rewrite)
Explicitly calling out the items most likely to be *unintentionally* dropped because they are invisible in documentation and only discoverable by reading code:
1. The practice-id-in-EncounterId parsing convention (RISK-03) — without it, no request can be routed to the correct database.
2. The Azure-mirror forwarding behavior (RISK-07) — dropping it could silently stop serving whichever practices are routed there today.
3. The `COLController`/Pegasus surface in its entirety (RISK-02), especially `SaveInvoice`'s idempotency contract (BR-15/BR-16).
4. The AWS-vs-on-prem DMS per-practice routing (RISK-01/BR-09) — dropping it could send documents to the wrong storage backend for practices already migrated to AWS.
5. The `"|&|"`/`"|?|"` in-band data protocol (RISK-12) between stored procedures and the API — if new stored procedures or a new data layer don't preserve or correctly translate this, "concept"-shaped fields (Text/Name/QualifierID/QualifierName/DateTaken) will silently come back empty.

## Recommendations
1. **Immediate, pre-migration action** (independent of timeline): rotate DB credentials (RISK-10) and treat the hard-coded encryption key as compromised (RISK-04); these are live exposures today, not migration risks.
2. Confirm with the client/business owner: is `COLController`/Pegasus still an active integration (RISK-02)? Is the Azure ERMS mirror still live (RISK-07)? Is `DAL`'s unused-by-ERMS 9 modules shared with HISO/KARO or another system (RISK-06)? These three answers materially change migration scope and must be resolved before Phase 2/3 design.
3. Do not port forward: per-practice `Web.config` connection strings (RISK-05), the hard-coded encryption scheme (RISK-04), the "fail open to HTTP 200" pattern, or the static `DbAccess` connection pattern found in the shared DAL (DatabaseAnalysis.md) — all are anti-patterns to leave behind, not carry into the unified platform.
4. Do port forward, deliberately re-implemented: the practice/tenant resolution *concept* (RISK-03) as an explicit, documented, testable mechanism; the AWS/on-prem document routing *decision point* (as a proper feature flag, not embedded per-record); and the invoice idempotency contract (BR-15) as an explicit API contract rather than a magic return-value convention.
5. Feed RISK-02, RISK-06, and RISK-07's open questions into Phase 4's cross-API comparison, since resolving them may depend on findings from the parallel HISO/KARO analyses (e.g., if HISO or KARO also reference the same shared `DAL` modules).
