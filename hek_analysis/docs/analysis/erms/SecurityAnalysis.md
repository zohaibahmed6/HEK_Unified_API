# ERMS Web API — Security Analysis (OWASP Top 10 Review)

## Summary
ERMS's data-access layer is well-protected against classic SQL injection (parameterized stored procedures throughout the reachable request path), but the application carries severe secrets-management, cryptography, and transport/config hygiene problems: hard-coded plaintext DB credentials, a hard-coded static encryption key used as an access-control primitive, wildcard CORS on a write endpoint, and sensitive data (tokens, patient identifiers, request bodies) written unredacted to plaintext log files.

## Findings

### SEC-01 — Hard-coded plaintext database credentials in `Web.config` (Critical)
15 connection strings are stored in cleartext in `Web.config`, including `User ID=pms_nz;Password=pms@@nz` repeated across every entry, several pointing at a public IP address (`43.255.162.58`) rather than an internal-only host.
- Evidence: `E:\NZTFS\ermsapi\DevLocal\ERMSWebAPI\ERMSWebAPI\Web.config`:
  `<add name="ConnIndiciDB" connectionString="Password=pms@@nz;Persist Security Info=True;User ID=pms_nz;Initial Catalog=PMS_NZ_EPX;Data Source=43.255.162.58"/>` (credential present, redacted above to the literal value already in the source file — flagged here verbatim only because it is already committed to source control in cleartext, not to further disclose it; treat this value as compromised and rotate).
- Impact: anyone with source/repo access (or a decompiled/extracted `Web.config` from a deployed instance) has full read/write DB credentials to production-adjacent data, for a database reachable over the public internet.
- Recommendation: rotate all credentials immediately; move to a secrets manager (Azure Key Vault, AWS Secrets Manager, etc.) or environment-variable injection at deploy time; restrict the SQL Server's firewall to known application IPs only; remove the public IP exposure if not required.

### SEC-02 — Custom cryptography with a hard-coded, static key used as an access-control primitive (Critical)
`Models/EncryptionManager.cs` implements AES (via `RijndaelManaged`) with a **32-byte key hard-coded in source** and a comment explaining the key is intentionally static so that IDs encoded by one process remain decodable by any other process indefinitely (see BusinessRules.md BR-20). This key is used to obfuscate Patient IDs and Encounter IDs that are then carried in URLs and used, in combination with the token check, as a de facto access-control gate on patient data.
- Evidence: `E:\NZTFS\ermsapi\DevLocal\ERMSWebAPI\ERMSWebAPI\Models\EncryptionManager.cs` lines 40-49:
  `myRijndael.Key = new byte[32] { 137, 10, 237, 69, 157, 169, 181, 70, 216, 110, 47, 209, 193, 153, 196, 109, 25, 146, 165, 140, 128, 7, 175, 122, 34, 247, 157, 143, 54, 233, 124, 219 };`
- Impact: anyone with the compiled DLL (or this source) can decrypt any patient/encounter ID ever generated by this system, and can also **encrypt arbitrary integers into valid-looking obfuscated IDs**, since encryption (not just decryption) uses the same exposed key: `GetEncryptedString(this int clearText)`. Combined with the fact that `int.TryParse` bypass lets **plain unencrypted integer IDs be submitted directly** (`GetDcrptValue`: `if (int.TryParse(value, out res)) return value;`), the "obfuscation" provides effectively no real access control — it is security-by-obscurity, and the obscurity itself is broken (key is public in the repo).
- Recommendation: this is not encryption at rest or in transit — it is an ID-obfuscation scheme masquerading as security. Replace with either (a) opaque server-issued session-scoped identifiers with no client-recoverable structure, or (b) real authorization checks (does this authenticated principal have rights to this patient?) instead of relying on ID secrecy. If encryption of identifiers is still desired, use per-environment keys sourced from a secrets manager, not a compiled constant.

### SEC-03 — SQL injection risk in DAL code adjacent to (but not currently reachable from) the ERMS controllers (High)
While `HSSDA.cs` and `PHCO.cs` (the classes actually called by `APIController`/`COLController`) use parameterized stored procedures exclusively, two other files in the same shared `DAL` project build SQL via string concatenation:
- `E:\NZTFS\ermsapi\DevLocal\DAL\DMS\DMSDA.cs` line 27: `cmd.CommandText = "Update Prompt.tblInboxFolderItem set DMSID='" + Guid + "' where InboxFolderItemID=" + InboxFolderItemID + "";`
- `E:\NZTFS\ermsapi\DevLocal\DAL\MHNHL7\DBMessages.cs` lines 797, 827, 860: e.g. `cmd.CommandText = "SELECT * FROM Config.tblScreeningTemplate where ScreeningTypeID in (" + templateIDs + ")";`
- Impact: **not exploitable through the current ERMS endpoints** (neither `APIController` nor `COLController` calls `DMSDA` or `DBMessages` in the reviewed source), but this code ships in the same `DAL.dll` and is a landmine if reused during consolidation, or if it is in fact reachable from another application sharing this DAL.
- Recommendation: parameterize these before any reuse; audit whether `DMSDA`/`DBMessages` are called from any other application sharing this DAL, since that would make this an actively exploitable, unreviewed injection point today.

### SEC-04 — Wildcard CORS on a controller with a financial write endpoint (High)
`COLController` is decorated `[EnableCors(origins: "*", headers: "*", methods: "*")]`, unconditionally, including on `SaveInvoice` (creates/updates billing service records).
- Evidence: `E:\NZTFS\ermsapi\DevLocal\ERMSWebAPI\ERMSWebAPI\Controllers\COLController.cs` line 20.
- Impact: any origin can issue cross-site requests to this controller from a victim's browser; combined with the token-in-header auth model this is lower-risk than cookie-based auth (no ambient credential to ride along), but if any client stores the token in a way accessible to script (e.g., `localStorage`) on a page that also loads attacker content (XSS elsewhere), wildcard CORS removes one of the layers that would otherwise limit blast radius.
- Recommendation: restrict `origins` to the specific known Pegasus/COL front-end domain(s).

### SEC-05 — No authentication/authorization framework; fails "open" to HTTP 200 (High)
See AuthenticationAuthorization.md for full detail. Every failed-auth path returns HTTP 200 with an `<Error>`/`error` JSON field rather than 401/403.
- Evidence: `SetToXml()` in `APIController.cs` always constructs `new HttpResponseMessage(HttpStatusCode.OK)` regardless of whether `error` is populated (lines 1667-1677); `COLController` actions do the same (`var response = new HttpResponseMessage(HttpStatusCode.OK); ... result = error;`).
- Impact: clients, proxies, and monitoring tools that key off HTTP status codes will not see authentication failures as failures; makes anomaly detection and rate-limiting-by-status-code ineffective.
- Recommendation: return proper 401 (invalid/missing token) and 403 (valid token, wrong resource) status codes.

### SEC-06 — Sensitive data logged in plaintext with no redaction or retention policy (High)
Every controller action logs the (by then decrypted) `PatientId`, `EncounterId`, `Practiceid`, and often full request/response bodies to flat files; `ERMSAPIProxy` additionally logs the full `Authorization` header (bearer token) verbatim when proxying to the Azure mirror.
- Evidence: `E:\NZTFS\ermsapi\DevLocal\ERMSWebAPI\ERMSWebAPI\Helpers\ERMSAPIProxy.cs` lines 24-30: `string forwardtoERMSAPIPostLog = $"...Authorization: {originalRequest.Headers.Authorization}\n..."; Logging.Instance.WriteEventLog(...)`. Also `APIController.cs`/`COLController.cs`, e.g. `WriteLog("In GetPatientData: PatientId: " + pmsPatientId + " ---- EncounterId: " + pmsEncounterId ...)` throughout.
- Impact: patient identifiers (PHI-adjacent) and live bearer tokens are persisted indefinitely in unencrypted, unrotated flat files (`Logs\IntegrationServices\...\*.txt`, see LoggingAnalysis.md) with no access control beyond filesystem permissions; a log file leak is equivalent to a data breach plus session-token theft.
- Recommendation: redact/hash patient identifiers and never log Authorization headers or full request bodies containing clinical content; adopt structured logging with field-level redaction policies before migration.

### SEC-07 — No rate limiting / brute-force protection (Medium)
No throttling, lockout, or rate-limiting is present anywhere in the reviewed code (`Web.config`, `Startup.cs`, controllers). `Authenticate` accepts unlimited username/password attempts.
- Recommendation: add rate limiting (API gateway or middleware level) in the unified platform; this is a gap to close in the rewrite, not a patch to the legacy app.

### SEC-08 — Debug compilation left enabled in base config (Low/Medium)
`<compilation debug="true" targetFramework="4.8"/>` in the base `Web.config`, only overridden by environment-specific transforms if those are correctly applied at deploy time.
- Evidence: `E:\NZTFS\ermsapi\DevLocal\ERMSWebAPI\ERMSWebAPI\Web.config`.
- Impact: if a transform is missed, verbose error pages/stack traces could be exposed.
- Recommendation: verify `Web.Release.config` correctly disables debug mode and that deploys always use the Release configuration.

### SEC-09 — Unsafe/uncontrolled document upload size and type validation (Medium)
`SaveDocument`/`SaveInvoice` accept base64 document content up to `maxRequestLength="10240"` KB (10 MB) with content-type inferred from a client-supplied string matched against a config-driven allow-list (`DMSDocTypes` app setting) — evidence: `DocumentTypeID()` in `APIController.cs`. There is no server-side content sniffing/validation that the actual bytes match the claimed type, and no antivirus/malware scanning is evident.
- Recommendation: add content-type verification (magic-byte sniffing) and malware scanning for uploaded documents in the redesigned platform.

### SEC-10 — Insecure deserialization exposure (Low, mitigated by usage pattern)
`XmlSerializer`/`Newtonsoft.Json.JsonConvert.DeserializeObject` are used to parse client-supplied XML/JSON directly into typed DTOs (`Authenticate`, `SaveDocument`, `SaveInvoice`). `XmlSerializer` used this way (typed, not `XmlSerializer` with `Type[]` from untrusted type names, and not `BinaryFormatter`/`NetDataContractSerializer`) is a comparatively low insecure-deserialization risk, and default `Newtonsoft.Json` settings (no `TypeNameHandling`) are also low risk. No `TypeNameHandling.Auto`/`All` was found in the codebase.
- Recommendation: no immediate action; confirm no `TypeNameHandling` is introduced in future changes, and re-verify in the migrated codebase.

## Evidence
See individual findings above; primary files: `Web.config`, `Models/EncryptionManager.cs`, `Models/EncryptedInt.cs`, `Helpers/ERMSAPIProxy.cs`, `Controllers/APIController.cs`, `Controllers/COLController.cs`, `DAL/DMS/DMSDA.cs`, `DAL/MHNHL7/DBMessages.cs`.

## Risks
Combined, SEC-01/SEC-02/SEC-05/SEC-06 mean this system currently has: credentials any repo-reader can use against a public-IP database, an ID-obfuscation scheme any binary-reader can defeat, no real authorization model, and PHI-adjacent data plus live session tokens sitting in plaintext logs. This is a **material clinical-data breach risk** independent of the migration project and should be flagged to the client as urgent regardless of the migration timeline.

## Recommendations
1. Immediately rotate the SQL credentials in `Web.config` and move them to a secrets manager — this is independent of and more urgent than the migration project.
2. Immediately treat the hard-coded Rijndael key as compromised; plan a controlled migration of any externally-persisted encrypted IDs (e.g., bookmarked URLs) if the key is rotated, or replace the whole ID-obfuscation approach with real authorization checks.
3. Restrict `COLController`'s CORS policy to known origins.
4. Redact patient identifiers and strip Authorization headers from all log output before any further operation of this system, legacy or migrated.
5. Carry none of SEC-01/02/04/05/06's *patterns* into the unified platform — they should inform "what not to do," not be treated as reusable design.
