# Phase 3 — Migration Classification (HISO / KARO / ERMS → Unified API)

**Scope:** This report classifies every meaningful module/component found across the three
Phase 1 analyses (`docs/analysis/hiso/`, `docs/analysis/karo/`, `docs/analysis/erms/`, 12 files
each) and the Phase 2 `ComparisonReport.md`, into exactly one of five migration dispositions:

- **Keep** — sound as-is, worth preserving in the new system.
- **Refactor** — capability needed and largely correct; implementation must change.
- **Merge** — duplicated across 2+ APIs; becomes one canonical implementation.
- **Replace** — current approach is fundamentally wrong for the new system; different technical
  approach needed even if the business need is kept.
- **Remove** — dead code, unused modules, stub/fake endpoints, or confirmed-obsolete functionality.

This is analysis and planning only. No code is written, no new architecture is designed here.
Every row cites the specific Phase 1/2 evidence it is based on. Where the source material does
not support a confident classification, that is stated explicitly rather than guessed.

## 1. Authentication & Security

| Module/Component | API(s) | Classification | Why |
|---|---|---|---|
| HISO session-GUID lookup (`GetSession`/`HealthLinkSession.GetByGUID`) | HISO | **Replace** | Not a credential exchange at all — possession of an opaque, non-expiring GUID grants full access; the lookup swallows all exceptions (`catch (Exception) { }`, `Mapper.cs` lines 1036-1046), making a DB outage indistinguishable from "invalid session." No expiry/single-use enforcement in the application layer (`hiso/AuthenticationAuthorization.md`). Cannot be extended into anything resembling real auth — needs a wholesale replacement. |
| KARO/ERMS custom bearer-token scheme (`Authenticate` → `[HSS].[uspInsertAndValidateToken]`, re-validated per call) | KARO, ERMS | **Merge → Replace** | Identical mechanism in both APIs (same stored procedure name, same DAL class `HSSDA.InsertAndValidateToken`) — first merge into one implementation, then replace outright: no framework auth (`<authentication mode="None"/>`, empty OWIN `Startup.Configuration`), no roles/claims, per-call DB round-trip. KARO never passes `expiryInDays` (always defaults in the SP); ERMS does wire it (`AppSettings["ExpiryInDays"]=0.5`) but neither enforces it independently in code. The one thing worth carrying forward *conceptually* (not as code) is the fine-grained scoping — token valid for a specific patient+encounter+practice tuple — per `ComparisonReport.md` §7/§11.2. |
| `SaveScreeningCode` (no token validation at all) | KARO | **Remove** | `APIController.cs` lines 1924-1947: deserializes and logs the payload, then unconditionally returns `{"status":"success"}` with **zero call to `InsertAndValidateToken`** — the sole endpoint across all three systems with no auth check whatsoever (`karo/SecurityAnalysis.md` finding #2, BR-06). Confirmed no-op — nothing persisted. Remove the stub; if the underlying capability (screening-code save) is still needed, it must be rebuilt from scratch, not "kept." |
| Rijndael/AES hardcoded key ID-obfuscation (`Models/EncryptionManager.cs`) | KARO, ERMS | **Merge → Replace** | Identical 32-byte hardcoded key literal in both codebases (`karo/SecurityAnalysis.md` finding #3, `erms/SecurityAnalysis.md` SEC-02), with a documented deliberate design comment in ERMS's source explaining the key is static *by design* ("hard coded key... else issue when application is stopped and started again" — ERMS BR-20). Both accept a fallback to plain unencrypted integers via `int.TryParse`, defeating the "protection" outright. This is being used as a security boundary for patient/encounter IDs and must not be carried forward in any form — real authorization (not ID obfuscation) must gate access to patient data in the unified platform. |
| Hardcoded SQL symmetric-key decryption password (`'tcpepms*1'` in `DALHelper.cs`/`DALHelperParameterCache.cs`) | HISO, KARO (confirmed); ERMS (likely, unconfirmed) | **Merge → Refactor** | Identical string across HISO and KARO's `DALHelper.cs` (`hiso/SecurityAnalysis.md` finding #2, `karo/SecurityAnalysis.md` finding #3) — strong evidence of a shared origin. Needs one secrets-management remediation (vault/config-based secret store), not three separate fixes. `> Unable to verify from available source` whether ERMS's copy of `DALHelper.cs` contains the identical string — `erms/SecurityAnalysis.md`/`DatabaseAnalysis.md` describe the same file/pattern but don't quote this specific line (`ComparisonReport.md` §2.7); confirm directly against ERMS source before assuming parity. |
| Plaintext DB credentials in `Web.config` (all three) | HISO, KARO, ERMS | **Merge → Replace** | HISO: 4 connections, one account (`pms_nz`/`pms@@nz`) reused across all. KARO: 6 environment variants, same credential pattern. ERMS: **worst of the three** — 15 connection strings, several pointing at a public IP `43.255.162.58` (`erms/SecurityAnalysis.md` SEC-01, confirmed "already occurring" exposure per `erms/RiskAssessment.md` RISK-10). Must become one config/vault-backed secret store, not per-app `Web.config` plaintext. |
| CORS misconfiguration (KARO whole controller wide open; ERMS `COLController`/`SaveInvoice` wide open, `APIController` commented-out) | KARO, ERMS | **Refactor** | KARO: `[EnableCors(origins:"*", headers:"*", methods:"*")]` on the entire `APIController` (`karo/SecurityAnalysis.md` finding #2). ERMS: wildcard CORS active specifically on `COLController`, which includes the financial `SaveInvoice` write (`erms/SecurityAnalysis.md` SEC-04). The capability (cross-origin access for legitimate portal clients) is presumably needed but must be an explicit, narrow allow-list per unified-platform security policy, not a wildcard. |
| Fault/exception detail leakage (`includeExceptionDetailInFaults="true"` in HISO; `debug="true"` in KARO/ERMS `Web.config`) | HISO, KARO, ERMS | **Merge → Refactor** | Same underlying anti-pattern (verbose internal errors reaching the client) in all three, just different mechanisms per stack (WCF fault detail vs ASP.NET debug compilation). One unified error-handling policy (generic client-facing errors + full detail only in server-side structured logs) replaces all three. |
| JWT/OAuth/OWIN/Identity/EF package references (unused scaffolding) | HISO (JWT libs), KARO/ERMS (full OAuth/Identity/EF stack) | **Remove** | HISO references `Microsoft.IdentityModel.JsonWebTokens`/`System.IdentityModel.Tokens.Jwt` with zero code constructing/validating a JWT anywhere (`hiso/TechnologyStack.md`). KARO and ERMS both reference the full `Microsoft.Owin.Security.OAuth/.Cookies/.Google/.Facebook/.Twitter/.MicrosoftAccount` and `Microsoft.AspNet.Identity.*` package set with an **empty** `Startup.Configuration()` body and no `ApplicationUser`/`UserManager`/`IdentityDbContext` anywhere (`karo/TechnologyStack.md`, `erms/TechnologyStack.md`, `ComparisonReport.md` §7). Vestigial, misleading scaffolding — remove; the new auth layer is built fresh. |
| ERMS `ERMSAPIProxy.cs` logging the live `Authorization` header verbatim when forwarding | ERMS | **Remove** (as implemented) | `Helpers/ERMSAPIProxy.cs` lines 24-30 logs the full outgoing request including the bearer token in plaintext (`erms/SecurityAnalysis.md` SEC-06). This specific behavior must not be ported; see also the Azure-mirror proxy itself under Infrastructure/Transport. |
| Unauthenticated/HTTP-200-fails-open response semantics | KARO, ERMS | **Merge → Replace** | Both APIs always return HTTP 200 regardless of outcome (error communicated only in the JSON/XML body) — `karo/SecurityAnalysis.md` finding #10, `erms/SecurityAnalysis.md` SEC-05, `ComparisonReport.md` §7/§8. Undermines WAF/gateway/SIEM tooling and violates basic REST semantics needed for a 10,000-user production platform. Replace with proper HTTP status semantics (401/403/409/etc.) as part of the new API contract design. |
| Unsafe file upload handling (`SaveDocument` — no size/magic-byte/AV validation) | KARO, ERMS (HISO N/A — no direct upload endpoint) | **Refactor** | KARO: no size limit at all (`karo/SecurityAnalysis.md` finding #7). ERMS: `maxRequestLength` caps at 10MB but still no content-sniffing/AV scan (`erms/SecurityAnalysis.md` SEC-09). The document-save capability is needed; validation must be added, not ported as-is. |
| Rate limiting | HISO, KARO, ERMS | **Replace** | None exists in any of the three (`ComparisonReport.md` §8). Not a "refactor" of existing code — there is nothing to refactor; this is net-new infrastructure required for the unified platform. |

## Migration Priority

### Must be fixed before anything ships to 10,000 concurrent users (hard blockers)

1. **Real authentication/authorization** — none of the three systems has one (HISO: GUID-only,
   no expiry; KARO/ERMS: hand-rolled bearer token, no framework auth, no roles). This is the
   single largest gap and blocks everything else — no clinical data should be exposed by the
   unified platform without a proper OAuth2/OIDC (or equivalent) layer designed from scratch.
2. **`DbAccess.cs` thread-unsafe static shared connection pattern** — confirmed live and
   reachable in HISO today; present (reachability varies) in KARO/ERMS. A static shared
   `SqlConnection`/`SqlCommand`/`SqlTransaction` cannot survive concurrent load at any
   meaningful scale, let alone 10,000 concurrent users. Must be eliminated entirely, not
   "fixed in place."
3. **All hardcoded secrets** — the SQL symmetric-key password (`'tcpepms*1'`), the Rijndael
   ID-obfuscation key, and plaintext DB credentials in `Web.config` (ERMS's public-IP exposure
   is an active incident, not a theoretical risk). One secrets-management remediation covering
   all three systems' known secrets.
4. **SQL injection in dormant DAL modules** (`DMSDA.cs`, `DBMessages.cs`) — currently
   unreachable from any of the three APIs' own controllers, but ships in the same compiled
   artifact. Must not be carried into the unified platform in any form without parameterization,
   regardless of whether the modules themselves are ultimately kept or retired.
5. **HTTP-200-always response semantics** — undermines every layer of production tooling (WAF,
   gateway, SIEM, client retry logic) that a 10,000-user platform depends on. Must be fixed as
   part of the new API contract, not patched onto the old controllers.
6. **CORS wildcards on endpoints touching patient/financial data** (KARO's entire controller,
   ERMS's `COLController`/`SaveInvoice`).
7. **Un-scoped/wildcard rate limiting (i.e., none)** — required before any production traffic at
   the target concurrency.

### Can be phased in after the above blockers are resolved

1. **Merge of the canonical clinical-data read surface** (demographics, conditions,
   medications, labs, notes, observations, documents) — high value, but functionally the
   platform can launch with even one system's endpoints live behind proper auth before all
   three are consolidated.
2. **Pegasus/OnlineClaim ("COL") consolidation** — real capability, but currently isolated to
   ERMS in production; can follow the core clinical-data merge.
3. **Document-generation consolidation** (Aspose rendering, AWS/on-prem DMS routing,
   MIME-vs-direction classification reconciliation) — needed, but document generation is a
   narrower slice of traffic than the core read/write clinical endpoints.
4. **Structured logging/observability layer** — should be designed early (it materially affects
   how blockers 1-2 above get monitored in production) but the full redaction/correlation-ID
   rollout across every endpoint can be incremental.
5. **Retirement decision on the 9-11 dormant DAL modules** — requires client confirmation of
   whether sibling applications outside this migration's scope depend on them; not a blocker for
   the unified platform's own launch, since none of these modules are reachable from any of the
   three APIs' own controllers today (Pegasus excepted, already covered above).
6. **Tenant/practice-onboarding data model replacement** — important for the "multiple
   locations" requirement, but the fixed connection-string approaches can be bridged/adapted in
   the short term while the proper tenant registry is built.
7. **Test suite build-out** — should start immediately in parallel with the above (informed by
   the business rules catalogued here and in the Phase 1 reports), but is not itself a
   pre-launch gate for the first migrated capability.
