## 2. Executive Summary

The organisation currently operates three independent, legacy clinical-integration APIs against a shared Indici Practice Management System (PMS) database: **HISO**, a WCF SOAP service implementing the NZ HISO 10014.2 "Form Session" standard for ACC45 accident-claim form exchange; **KARO** (`HSSWebAPI`), an ASP.NET Web API 2 bridge between the Indici PMS and the HSS portal; and **ERMS** (`ERMSWebAPI`), an ASP.NET Web API 2 service exposing eReferrals data (XML) and a second, undocumented "COL"/Pegasus claiming integration (JSON). All three were independently reverse-engineered in Phase 1, cross-compared in Phase 2, and classified for migration disposition in Phase 3 (`ComparisonReport.md`, `MigrationRecommendations.md`).

The three systems were found to share a single underlying `DAL` codebase (identical subfolder/class names, identical hardcoded secrets, identical SQL-injection code smells in dormant modules), the same authentication anti-pattern (custom bearer token re-validated per call against `[HSS].[uspInsertAndValidateToken]`, no framework-level auth), and near-total duplication of clinical read endpoints (demographics, conditions, medications, labs, notes, observations, documents) under different serialization formats (`ComparisonReport.md` §2, §5). None of the three systems has real authentication, all three log PHI/secrets in plaintext, and all three carry critical hardcoded-secret and dormant-SQL-injection exposure (`ComparisonReport.md` §7–§9, `MigrationRecommendations.md` §1).

The purpose of modernization is to replace these three overlapping, insecure, non-scalable legacy integrations with a single **Unified Healthcare API** that: (a) preserves the confirmed clinical business rules and data contracts each legacy system currently fulfils; (b) consolidates duplicated capability into one canonical implementation per capability; (c) replaces every current authentication, secrets-management, logging, and multi-tenancy mechanism, none of which is fit for purpose; and (d) is designed to support a stated target of 10,000 concurrent users across multiple practice locations (`MigrationRecommendations.md` "Migration Priority").

Business goals: eliminate duplicated maintenance effort across three codebases; close critical security exposures (hardcoded credentials, one of which is an active public-IP exposure incident per `erms/RiskAssessment.md` RISK-10 as cited in `ComparisonReport.md` §8); provide a single auditable platform for regulators/PHOs; and enable practice onboarding without code redeployment.

Expected outcome: one unified, securable, horizontally-scalable Healthcare API that exposes the confirmed clinical and financial capabilities of HISO, KARO, and ERMS through a single canonical contract, informed by — but not a direct port of — the three legacy implementations.

> This SRS is a requirements document. It does not propose the unified platform's target architecture, technology stack, or code; those are explicitly out of scope per the task instructions and belong to a subsequent Architecture Design phase.

## 4. Existing System Overview

### 4.1 HISO

WCF SOAP service (`FormSessionService.svc`, contract `FormSessionPortType`, 6 operations: `getVersion`, `getDeliveryOptions`, `getData`, `saveContainer`, `getFormView`, `processAction`) implementing the HISO 10014.2 "Form Session" specification for ACC45 accident-claim form exchange with NZ HealthLink-style clinical form engines. Key capabilities: database-driven "concept" mapping of HL7/HISO concept names to stored procedures/columns (`ConceptMapper/HisoConceptDetail.cs`); ACC45 form builder/save engine; server-side document rendering via Aspose (HTML/image → PDF/DOCX); DMS/AWS document storage. (`hiso/ExecutiveSummary.md`, `hiso/EndpointInventory.md`)

Key limitations: session identified by opaque, non-expiring GUID with no credential exchange (`hiso/AuthenticationAuthorization.md`); thread-unsafe static shared DB connection state confirmed live and reachable (`hiso/SecurityAnalysis.md` finding #5); business rules embedded in `Web.config` appSettings; several dead/stub code paths (`static mode` in `getData`, `addInvoice`/`launchForm` actions, unreachable code in `saveProcessAction`) whose intended behavior is not documented (`hiso/DocumentationGap.md`).

### 4.2 KARO (HSSWebAPI)

ASP.NET Web API 2 "fat controller" (`APIController`, 2,047 lines, 24 endpoints) bridging the Indici PMS and the HSS portal: patient demographics, clinical notes, conditions, medications, labs, observations, recalls, documents, invoices, and templated "encounter summary" clinical forms. Calls only `DAL\South\HSSDA.cs` of a much larger shared DAL that ships 11 additional, uncalled integration modules. (`karo/ExecutiveSummary.md`, `karo/Architecture.md`)

Key limitations: no framework-level authentication (`<authentication mode="None"/>`, empty OWIN `Startup`); wide-open CORS on the entire controller; `SaveScreeningCode` performs no token validation at all and always reports fake success; `GetEncounterSummary` returns hardcoded mock data regardless of the requested patient; all responses return HTTP 200 regardless of outcome. (`karo/ExecutiveSummary.md`, `karo/BusinessRules.md` BR-06/BR-09)

### 4.3 ERMS (ERMSWebAPI)

ASP.NET Web API 2 application exposing two controllers: `APIController` (23 XML endpoints implementing the documented HISO-concept eReferrals contract for the South Island NZ eReferrals platform) and `COLController` (7 JSON endpoints, entirely undocumented, integrating with a "COL"/Pegasus claiming-adjacent system, including a financial `SaveInvoice` write). Sits on the same shared DAL project as KARO, additionally activating the `Pegasus\PHCO.cs` module that is dormant in KARO. (`erms/ExecutiveSummary.md`, `ComparisonReport.md` §2.1)

Key limitations: 15 connection strings in `Web.config`, several pointing at a public IP address — the most exposed credential footprint of the three systems (`erms/SecurityAnalysis.md` SEC-01, `ComparisonReport.md` §8); wildcard CORS active on `COLController`, which includes the financial `SaveInvoice` endpoint; a proxy (`ERMSAPIProxy.cs`) that silently forwards requests for PHO-tagged practices to a separate Azure-hosted mirror and logs the live bearer token in plaintext while doing so (`erms/BusinessRules.md` BR-04, `erms/SecurityAnalysis.md` SEC-06).

### 4.4 Common Capabilities Across All Three

All three systems: (1) sit on the same underlying Indici PMS SQL Server database; (2) use a proprietary, non-standard flat-file `Logger.dll` with no correlation IDs, no log levels, and PHI/secret exposure in logs; (3) integrate with the same precompiled `AWSDoc.dll` for AWS-backed document storage, checked per-practice; (4) share the identical hardcoded SQL symmetric-key decryption password `'tcpepms*1'` in `DALHelper.cs` (confirmed in HISO and KARO; not directly confirmed, though structurally likely, in ERMS); (5) have no automated tests, no rate limiting, and no security-event/audit logging. (`ComparisonReport.md` §2, §8, §9)

## 5. Project Objectives

### 5.1 Business Objectives

- Consolidate three independently maintained, duplicated clinical-data integrations into one platform, reducing maintenance and onboarding cost (`ComparisonReport.md` §11).
- Preserve all confirmed clinical, financial, and document-handling business rules currently relied upon by HISO, KARO, and ERMS consumers (this SRS, Section 9).
- Provide a single, auditable integration surface for practices, PHOs, and regulatory reporting.
- Support onboarding of new practices/locations without a code deployment (`MigrationRecommendations.md` §2, "Tenant/practice-onboarding data model replacement").

### 5.2 Technical Objectives

- Replace the three parallel, near-duplicate clinical-data read implementations with one canonical data-access surface (`ComparisonReport.md` §5, §11.3).
- Consolidate the shared-but-inconsistent DAL codebase into a single, tested component, retiring or explicitly re-scoping the 9–11 dormant integration modules pending client confirmation (`MigrationRecommendations.md` §2, "Items explicitly unresolved").
- Move off end-of-investment technology (.NET Framework 4.8, WCF SOAP hosting, OWIN) onto a supportable stack — the specific target stack is an Architecture Design decision, out of scope for this SRS (`MigrationRecommendations.md` §6).

### 5.3 Migration Objectives

- Classify and dispose of every legacy module per the Keep/Refactor/Merge/Replace/Remove taxonomy established in `MigrationRecommendations.md`, honoring that classification in the unified platform's requirements (see Section 17).
- Resolve every explicitly flagged ambiguous/dead code path (HISO's `static mode`, `addInvoice`/`launchForm`, KARO's `GetEncounterSummary`/`SaveScreeningCode`) via business sign-off before functional parity is declared, not by silent inference (`hiso/DocumentationGap.md`, `karo/BusinessRules.md` BR-06/BR-09, `MigrationRecommendations.md` §3).

### 5.4 Security Objectives

- Replace all three legacy authentication mechanisms with one real authentication/authorization layer; **Requirement cannot be confirmed from analysis** as to which specific standard (OAuth2/OIDC or other) — the analysis reports recommend this direction but do not mandate a specific protocol (`ComparisonReport.md` §11.2, `MigrationRecommendations.md` §1).
- Eliminate all hardcoded secrets (SQL symmetric-key password, Rijndael ID-obfuscation key, plaintext DB credentials in `Web.config`) via a single secrets-management remediation (`MigrationRecommendations.md` §1).
- Parameterize or remove the confirmed SQL-injection code paths in the dormant DAL modules (`DMSDA.cs`, `DBMessages.cs`) before any of that code is carried forward in any form (`MigrationRecommendations.md` §1, §2).
- Establish HTTP status-code semantics that reflect actual outcomes, replacing the current "always HTTP 200" pattern in KARO and ERMS (`ComparisonReport.md` §7, §8).

### 5.5 Performance Objectives

- Support a stated target of 10,000 concurrent users across multiple practice locations (`MigrationRecommendations.md` "Migration Priority" section references this target explicitly as the basis for several hard-blocker classifications). **Requirement cannot be confirmed from analysis**: no specific latency, throughput, or SLA figures are present in any Phase 1–3 report; these must be obtained from the business before the Architecture Design phase finalizes capacity planning.

### 5.6 Scalability Objectives

- Eliminate the thread-unsafe static shared DB connection pattern (`DbAccess.cs`), confirmed live and reachable in HISO today, present with varying reachability in KARO/ERMS (`MigrationRecommendations.md` §2, "Migration Priority" item 2).
- Replace the per-practice `Web.config` connection-string-name convention (12 targets in KARO, 15 in ERMS, each requiring a config change and redeploy to onboard a practice) with a data-driven tenant registry (`ComparisonReport.md` §11.10, §6).
- Bound the currently-unbounded `Parallel.ForEach` stored-procedure execution in HISO's concept-mapping engine to avoid SQL connection-pool exhaustion at scale (`hiso/RiskAssessment.md` R-10, `MigrationRecommendations.md` §6).

## 6. Scope

### 6.1 Included

- One canonical clinical-data access surface covering: patient demographics, clinical/consult notes, conditions/diagnoses, medications, lab and radiology results, documents/attachments, provider/practitioner lookup, recalls, observations/measurements, and invoicing — consolidating the overlapping capabilities of HISO's `getData`, KARO's `APIController`, and ERMS's `APIController`/`COLController` (`ComparisonReport.md` §5).
- ACC45 (ACC accident-claim) form building and save capability, unique to HISO, including the concept-mapping design pattern (`ComparisonReport.md` §3, `MigrationRecommendations.md` §3).
- Templated "encounter summary" clinical forms (diabetes review, foot exam, retinopathy), unique to KARO, schema-driven (`karo/BusinessRules.md` BR-10/BR-11).
- The Pegasus/OnlineClaim ("COL") integration, dormant in KARO but live in ERMS, to be implemented exactly once, informed by ERMS's live usage (`MigrationRecommendations.md` §2, §8).
- One document generation and storage service, consolidating HISO's Aspose-based server-side rendering and the shared two-step "DMS write + PMS index" pattern with AWS/on-prem routing (`ComparisonReport.md` §2.8, §11.4).
- One authentication/authorization layer, one secrets-management approach, one structured/correlated/redacted logging layer, and one tenant/practice-resolution service, replacing all three systems' equivalents (`ComparisonReport.md` §11.2, §11.5, §11.6, §11.1).
- A single, versioned, documented idempotency contract for duplicate-submission handling (currently magic return codes `-3`/`-5`), replacing the undocumented per-stored-procedure conventions (`ComparisonReport.md` §11.9).

### 6.2 Excluded

- Physical database schema redesign of the underlying Indici PMS — the analysis reports describe the PMS as an external system the unified API integrates with, not a target of this migration (`ComparisonReport.md` §6, "the actual T-SQL definitions behind the ~35-40 stored procedures... were not available").
- The 9–11 dormant shared-DAL modules (BPAC, BPI, GP2GP, MHNAppointment, MHNHL7, Procare, Procon, Screening, UI, DMSAWS) are excluded from the unified platform's own codebase pending explicit client confirmation of whether they serve sibling applications outside HISO/KARO/ERMS's scope (`MigrationRecommendations.md` §2, "Items explicitly unresolved"). **Requirement cannot be confirmed from analysis** as to their final disposition.
- Architecture, technology-stack selection, and implementation code — explicitly out of scope for this SRS per the task instructions; this document defines requirements only.
- The "Azure ERMS API" mirror-forwarding mechanism's continued operation cannot be confirmed as still required — `erms/RiskAssessment.md` (as cited in `MigrationRecommendations.md` §6) flags that the target Azure mirror may itself be defunct and must be verified with the client before assuming any traffic depends on it.

### 6.3 Future Enhancements

- Rate limiting, structured/correlated logging, and security-event/audit logging are classified as net-new infrastructure not present in any of the three legacy systems; while required before production launch at the target scale, their full rollout may be phased in after initial capability parity is reached (`MigrationRecommendations.md` "Migration Priority — Can be phased in after the above blockers are resolved").
- A comprehensive automated test suite, informed by the business rules catalogued in this SRS, is identified as necessary but not itself a pre-launch gate for the first migrated capability (`MigrationRecommendations.md` §6, "Migration Priority" item 7).

|---|---|

## 10. Use Cases

The following use cases are derived from confirmed endpoint behavior in the three systems' `EndpointInventory.md` reports. Each represents a canonical capability the unified platform must support.

### UC-01: Retrieve Patient Clinical Data

- **Actors:** Authenticated Provider/Practitioner (via HSS portal, ERMS eReferrals platform, or HISO-consuming form engine)
- **Preconditions:** Caller holds a valid, non-expired credential scoped to the requested patient+encounter+practice.
- **Flow:** (1) Caller authenticates and obtains a credential (FR-AUTH-01). (2) Caller requests one of demographics, notes, conditions, medications, or lab results for a specific patient/encounter (FR-PAT-01, FR-CLIN-01, FR-COND-01, FR-MED-01, FR-LAB-01). (3) Platform resolves practice/tenant context (FR-TEN-01). (4) Platform validates authorization scope (FR-AUTH-02). (5) Platform returns the requested clinical data.
- **Alternative Flow:** If the credential is expired or invalid, the platform returns an explicit unauthorized response (not the legacy "always HTTP 200" pattern — see FR-HTTP-01 in Section 13).
- **Postconditions:** Requested data is returned to the caller; no state is modified.
- **Business Rules:** HISO-BR-01/02/03/08/09/10, KARO-BR-01/02/03/05, ERMS-BR-01/02/03/05/06.

### UC-02: Save Clinical Condition/Diagnosis

- **Actors:** Authenticated Provider/Practitioner
- **Preconditions:** Caller holds a valid credential scoped to the target patient+encounter+practice.
- **Flow:** (1) Caller submits a diagnosis/condition payload (FR-COND-01). (2) Platform validates authorization scope. (3) Platform persists the condition. (4) If the condition already exists for the current appointment, platform returns a documented success/conflict response rather than an error (FR-COND-02, FR-IDEM-01).
- **Alternative Flow:** If validation fails (e.g., malformed payload), platform returns an explicit error with a non-200 status code.
- **Postconditions:** Condition is persisted (or duplicate is acknowledged without a second write).
- **Business Rules:** KARO-BR-12, ERMS-BR-15 (idempotency pattern), KARO-BR-21 (long-term flag handling).

### UC-03: Save and Retrieve a Document

- **Actors:** Authenticated Provider/Practitioner or Administrative staff
- **Preconditions:** Caller holds a valid credential; document content is base64-encoded or otherwise transportable per the API contract.
- **Flow:** (1) Caller submits document content with an `ItemType` (in/out) and MIME/content type (FR-DOC-01/02/03). (2) Platform determines AWS vs. on-prem DMS routing per practice configuration (Section 16). (3) Platform writes binary content to DMS, then writes a PMS-side index record referencing the DMS key (two-step pattern, Section 14). (4) Platform returns the assigned document key. (5) On later retrieval, caller supplies the document key or filter criteria (FR-DOC-04) and platform returns the content.
- **Alternative Flow:** If the DMS write succeeds but the PMS index write fails (or vice versa), the platform must apply an explicitly designed failure/compensation behavior — the legacy pattern has no distributed transaction across the two steps and no documented compensation (see Section 17, Risks).
- **Postconditions:** Document is stored and indexed; retrievable via the unified endpoint.
- **Business Rules:** HISO-BR-12/21/22, KARO-BR-15/16/17/18, ERMS-BR-08/09/10/19.

### UC-04: Submit an ACC45 Accident Claim Form

- **Actors:** HealthLink-style clinical form engine (on behalf of a Provider)
- **Preconditions:** Caller holds a valid session credential (replacing HISO's GUID-only session).
- **Flow:** (1) Form engine requests form data via the concept-mapping mechanism (FR-BILL-02, HISO-BR-03/08/09/10). (2) Provider completes the form. (3) Form engine submits the completed form. (4) Platform renders the form view and saves it to DMS. (5) Platform persists ACC45 definition/diagnosis/referral data, linked to the DMS document GUID (HISO-BR-12).
- **Alternative Flow:** Field-level parsing exceptions (e.g., malformed `employmentStatus`, non-numeric diagnosis "side") are handled per HISO-BR-13/14/15, rebuilt with sound parsing rather than the current fragile string-splitting.
- **Postconditions:** ACC45 claim is persisted and linked to its rendered document.
- **Business Rules:** HISO-BR-12 through BR-18.

### UC-05: Submit an Invoice (Billing)

- **Actors:** Authenticated billing-capable caller (KARO consumer or ERMS COL/Pegasus consumer)
- **Preconditions:** Caller holds a credential with elevated authorization for financial writes, distinct from read-only clinical access (per FR-BILL-01).
- **Flow:** (1) Caller submits invoice/service data. (2) Platform validates authorization scope specifically for financial operations. (3) Platform persists the invoice. (4) If the invoice already exists, platform returns a documented success/conflict response (FR-IDEM-01).
- **Alternative Flow:** Unauthorized or malformed submissions are rejected with an explicit error status.
- **Postconditions:** Invoice is persisted (or duplicate acknowledged).
- **Business Rules:** KARO-BR-13, ERMS-BR-15/16.

### UC-06: Onboard a New Practice/Tenant

- **Actors:** System Administrator
- **Preconditions:** Administrator has platform-admin authorization.
- **Flow:** (1) Administrator registers a new practice in the tenant registry (FR-TEN-01, FR-ADMIN-01) with its connection/data-routing configuration. (2) No application redeployment occurs. (3) New practice's data becomes accessible through the unified endpoints once resolution rules are in effect.
- **Alternative Flow:** N/A — **Requirement cannot be confirmed from analysis** as to the specific onboarding workflow steps, since none of the three legacy systems has a data-driven onboarding process to reverse-engineer (all three require a config change plus redeploy).
- **Postconditions:** New practice is queryable through the unified platform.
- **Business Rules:** KARO-BR-03, ERMS-BR-01.

## 12. Security Requirements

### 12.1 Authentication

- The platform must implement one real authentication mechanism, replacing HISO's GUID-only session (no credential exchange, no expiry, swallowed exceptions on lookup failure) and KARO/ERMS's hand-rolled bearer token (no framework auth, `<authentication mode="None"/>`, empty OWIN `Startup`). (`ComparisonReport.md` §7, `MigrationRecommendations.md` §1)
- **Requirement cannot be confirmed from analysis** as to the specific protocol (OAuth2/OIDC vs. another standard) — this is a design recommendation in the source reports, not a confirmed mandate.

### 12.2 Authorization

- Authorization must be scoped per patient+encounter+practice, per FR-AUTH-02, preserving the one legitimate design input from KARO/ERMS (fine-grained scoping) while discarding the insecure implementation (DB round-trip per call, no roles/claims). (`ComparisonReport.md` §7, §11.2)
- Financial write endpoints (invoicing) require authorization distinct from read-only clinical access — the legacy ERMS `COLController.SaveInvoice` had no such distinction and sat behind wildcard CORS. (`erms/SecurityAnalysis.md` SEC-04, `MigrationRecommendations.md` §3)

### 12.3 JWT / Tokens

- If tokens are used, they must have enforced, non-bypassable expiry (see FR-AUTH-03). Legacy JWT/OAuth/OWIN/Identity package references in all three systems are vestigial (never wired to actual token issuance/validation code) and must not be treated as evidence of an existing, reusable auth implementation. (`ComparisonReport.md` §7, `MigrationRecommendations.md` §1)

### 12.4 Refresh Tokens

**Requirement cannot be confirmed from analysis.** None of the three legacy systems implements a refresh-token mechanism; all three re-validate a single token against the database on every call.

### 12.5 Password Policies

**Requirement cannot be confirmed from analysis.** No password complexity, rotation, or lockout policy is documented in any Phase 1–3 report for any of the three systems.

### 12.6 OWASP Alignment

- The unified platform must remediate every OWASP-relevant finding confirmed across the three systems: broken authentication (all three), injection (confirmed SQL injection in dormant `DMSDA.cs`/`DBMessages.cs`), security misconfiguration (wildcard CORS, debug mode enabled, exception detail leakage), sensitive data exposure (hardcoded secrets, plaintext credentials, PHI in logs), and insufficient logging/monitoring (no security-event logging in any system). (`ComparisonReport.md` §8, §9, `MigrationRecommendations.md` §1)

### 12.7 Encryption

- All hardcoded cryptographic material must be eliminated: the SQL symmetric-key decryption password `'tcpepms*1'` (confirmed in HISO and KARO's `DALHelper.cs`; structurally likely but **not directly confirmed** in ERMS — Section 18) and the static Rijndael/AES key used to obfuscate patient/encounter IDs in KARO and ERMS (`Models/EncryptionManager.cs`), which both accept a fallback to unencrypted plain integers via `int.TryParse`, defeating the "protection" outright. ID obfuscation must not be relied upon as an access-control boundary in the unified platform — real authorization must gate patient-data access. (`ComparisonReport.md` §2.1, §2.7, `MigrationRecommendations.md` §1)

### 12.8 Audit Logging

- Security-event/audit logging (failed authentication attempts, access events distinguishable from debug tracing) is required and is net-new: none of the three systems has any such capability today — HISO's failed session lookups are indistinguishable from generic DB errors due to a swallowed-exception pattern. (`ComparisonReport.md` §9, `MigrationRecommendations.md` §5)

### 12.9 Rate Limiting

- Rate limiting is required and is net-new infrastructure — confirmed absent in all three systems. (`ComparisonReport.md` §8, `MigrationRecommendations.md` §1, "Migration Priority" item 7)

### 12.10 Secrets Management

- One centralized secrets-management approach (vault/config-store-backed) must replace all `Web.config` plaintext credentials across all three systems — ERMS's exposure is the most severe, with several of 15 connection strings pointing at a public IP address, described in the source reports as an active incident rather than a theoretical risk. (`erms/SecurityAnalysis.md` SEC-01, `erms/RiskAssessment.md` RISK-10, `MigrationRecommendations.md` §1)

### 12.11 Secure Headers

**Requirement cannot be confirmed from analysis.** No Phase 1–3 report documents current HTTP security-header usage (or absence) in any of the three systems.

### 12.12 CORS Policy

- CORS must be an explicit, narrow allow-list per unified-platform security policy, replacing KARO's wildcard CORS on its entire controller and ERMS's wildcard CORS specifically on `COLController` (which includes the financial `SaveInvoice` write), while ERMS's `APIController` currently has CORS commented out (an inconsistent trust boundary between the two ERMS controllers that must be resolved explicitly, not silently inherited). (`karo/SecurityAnalysis.md` finding #2, `erms/SecurityAnalysis.md` SEC-04, `MigrationRecommendations.md` §1)

### 12.13 Input Validation

- Input validation must be added to file-upload/document-save paths that currently have none: KARO's `SaveDocument` has no size limit, no content/magic-byte validation, and no AV scanning; ERMS caps request size at 10MB but has no content-sniffing or AV scan either. (`karo/SecurityAnalysis.md` finding #7, `erms/SecurityAnalysis.md` SEC-09, `MigrationRecommendations.md` §1)
- Typed field validation must replace KARO's loose `JObject`-based encounter-summary field validation, where posted field types must match schema type except `Float` is always silently accepted for integer fields (KARO-BR-11). (`MigrationRecommendations.md` §3)

### 12.14 Output Encoding

- Exception/fault detail must not reach clients: HISO's `includeExceptionDetailInFaults="true"` leaks internal exception messages via SOAP faults; KARO/ERMS's `debug="true"` in `Web.config` similarly risks verbose error exposure. A single unified error-handling policy (generic client-facing errors, full detail only in server-side structured logs) must replace all three mechanisms. (`ComparisonReport.md` §8, `MigrationRecommendations.md` §1)

## 13. API Requirements

### 13.1 REST Standards

- The unified platform's API contract must be REST/JSON-based (or another modern contract per Architecture Design decision, out of scope here), replacing HISO's WCF SOAP transport, which has no first-class modern .NET hosting support. (`ComparisonReport.md` §1, §3, `MigrationRecommendations.md` §6)

### 13.2 Versioning

**Requirement cannot be confirmed from analysis.** No API versioning scheme is documented in any of the three legacy systems' Phase 1 reports.

### 13.3 Response Format

- The API must define a single, consistent response envelope, replacing the current split between KARO's JSON, ERMS `APIController`'s XML, and ERMS `COLController`'s JSON for functionally equivalent capabilities. Whether the unified platform must support multiple serialization formats (to preserve existing consumer contracts) is a stakeholder decision; the analysis reports recommend "one canonical data-access surface with contract adapters if needed." (`ComparisonReport.md` §5, §11.3)

### 13.4 ProblemDetails / Error Format

- Errors must be communicated via explicit, standard HTTP status semantics, not embedded solely in a 200-status response body as KARO and ERMS currently do. (`ComparisonReport.md` §7, §8, `MigrationRecommendations.md` §1)

### 13.5 Pagination

**Requirement cannot be confirmed from analysis.** None of the three Phase 1 `EndpointInventory.md` reports documents pagination on any list-returning endpoint (e.g., `GetAccidents`, `GetConsultNotes`); all appear to return the full filtered result set.

### 13.6 Filtering

- Filtering by date range (min/max) is a confirmed pattern across multiple list endpoints (e.g., ERMS's `GetConsultNotes`, `GetLaboratoryReportList`) and must be preserved. (`erms/EndpointInventory.md`)

### 13.7 Sorting

- Sort-order support (ascending/descending by date) is a confirmed pattern in ERMS's list endpoints (`pmsOrder` parameter, annotated in the response via ERMS-BR-12) and should be preserved as an explicit, documented parameter. (`erms/BusinessRules.md` BR-12)

### 13.8 Validation

- See Section 12.13 (Input Validation).

**Requirement cannot be confirmed from analysis.** No Phase 1–3 report documents OpenAPI/Swagger tooling in any of the three legacy systems; HISO's WCF service exposes only a WSDL. This may be a beneficial addition for the unified platform but is not a confirmed migration requirement.

| Confirmed no-op/stub endpoints (`SaveScreeningCode`, `GetEncounterSummary`, HISO's `addInvoice`/`launchForm`/static-mode branch) | Remove, pending stakeholder sign-off | Confirmed fake/dead behavior; if genuinely needed, must be rebuilt from scratch, not "kept." | `MigrationRecommendations.md` §3 |

### 17.2 Migration Phases (Priority Order per Source Analysis)

**Phase A — Hard blockers (must be resolved before any production traffic at target concurrency):**
1. Real authentication/authorization layer.
2. Elimination of `DbAccess.cs`'s thread-unsafe static shared connection pattern.
3. Elimination of all hardcoded secrets (SQL symmetric-key password, Rijndael key, plaintext DB credentials).
4. Parameterization/removal of SQL injection in dormant DAL modules.
5. Correct HTTP status-code semantics.
6. Narrow, explicit CORS policy on all endpoints touching patient/financial data.
7. Rate limiting.

**Phase B — Can be phased in after Phase A:**
1. Merge of the canonical clinical-data read surface.
2. Pegasus/OnlineClaim ("COL") consolidation.
3. Document-generation consolidation (Aspose rendering, AWS/on-prem routing, MIME-vs-direction classification reconciliation).
4. Structured logging/observability rollout (design should start early; full redaction/correlation-ID rollout across every endpoint can be incremental).
5. Retirement decision on the 9–11 dormant DAL modules, pending client confirmation.
6. Tenant/practice-onboarding data model replacement (legacy connection approaches may be bridged/adapted short-term).
7. Test suite build-out (should start immediately in parallel; not itself a pre-launch gate for the first migrated capability).

(Source: `MigrationRecommendations.md`, "Migration Priority" section, verbatim structure preserved for traceability.)

## 18. Assumptions

- It is assumed the underlying Indici PMS database schema and stored procedures remain externally owned and largely unchanged during this migration; no Phase 1–3 report proposes PMS schema changes.
- It is assumed that where a legacy behavior is classified "Remove, pending client confirmation" (the 9–11 dormant DAL modules, `Procare`/`Procon`, HISO's dead code branches), the business will provide an explicit decision before final deletion — this SRS does not assume removal is safe by default. (`MigrationRecommendations.md` §2, "Items explicitly unresolved")
- It is assumed the "10,000 concurrent users, multiple locations" target cited in `MigrationRecommendations.md` reflects an actual business requirement, though its specific source (business stakeholder vs. architectural planning assumption) is not documented in the Phase 1–3 reports supplied.
- It is assumed HISO's, KARO's, and ERMS's respective external consumers (HealthLink-style form engines, the HSS portal, the ERMS eReferrals platform, and the COL/Pegasus system) will need to be migrated or bridged to the unified API's new contract; the specific migration/cutover approach for each consumer is not addressed in the source reports.

## 19. Constraints

- The unified platform must integrate with the existing Indici PMS SQL Server database and its existing stored-procedure contracts, whose full T-SQL definitions were not available to any Phase 1 report. (`ComparisonReport.md` §11, closing note)

|---|---|---|---|
| Silent behavioral drift during merge of KARO/ERMS's near-duplicate clinical-data endpoints (JSON vs. XML, different field names) | Consumers of the legacy JSON/XML contracts could break if the unified contract diverges without an adapter | Preserve legacy field-shape contracts via serialization adapters until consumers migrate, or coordinate a breaking-change rollout with each consumer explicitly | **Requirement cannot be confirmed from analysis** — no owner is named in source reports |

| Azure ERMS mirror may be defunct, or may still carry live traffic | Either silently dropping or silently preserving the Azure-forwarding proxy risks breaking traffic or reproducing a security-sensitive (token-logging) behavior | Verify with the client whether `https://deverms.vitonta.com` (or its current equivalent) is still live before deciding | `MigrationRecommendations.md` §6 |
| AWS-fallback-on-exception behavior may differ genuinely between HISO and KARO/ERMS, or may simply be under-documented | Silently adopting one system's fallback behavior for all three could change reliability characteristics unexpectedly | Confirm against the live database/stored-procedure definitions before finalizing the document-storage abstraction's fallback policy | `ComparisonReport.md` §4, §11.4 |

## 21. Acceptance Criteria

The unified platform's first release is considered ready for stakeholder acceptance when:

1. All Phase A "hard blocker" items in Section 17.2 are demonstrably resolved (real auth, no thread-unsafe shared connections, no hardcoded secrets, no reachable SQL injection, correct HTTP status semantics, explicit CORS allow-lists, rate limiting in place).
2. Every Functional Requirement in Section 8 marked "Must-have" is implemented and traceable to at least one automated test.
3. Every business rule in Section 9 catalogued as High priority is either preserved (with a passing test demonstrating the preserved behavior) or explicitly retired with documented business sign-off.
4. Every item in this document marked **"Requirement cannot be confirmed from analysis"** has been resolved via stakeholder confirmation and, where it resulted in a new requirement, that requirement has been added to a revised version of this SRS.
5. The canonical clinical-data read surface (Section 8.2–8.6) returns data for at least one legacy system's full endpoint set behind the new authentication layer, per the phased rollout in Section 17.2, Phase B item 1.
6. A documented, versioned idempotency contract (FR-IDEM-01) is in place for all write endpoints previously relying on undocumented magic return codes.

**Requirement cannot be confirmed from analysis** for any quantitative acceptance thresholds (e.g., specific latency targets, specific uptime percentage, specific concurrent-user load test results) — none are documented in the source Phase 1–3 reports beyond the qualitative "10,000 concurrent users" target cited in `MigrationRecommendations.md`.
